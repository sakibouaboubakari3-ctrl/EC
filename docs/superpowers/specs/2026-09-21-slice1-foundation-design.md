# EspaceCredit — Slice 1: Foundation & End-to-End Slice

Status: Approved for planning
Date: 2026-09-21
Source: `EspaceCredit_Master_Prompt.md` (§1–§7), scoped down per decomposition below

## 1. Purpose

EspaceCredit is a bilingual (FR/EN) online lending platform: borrowers apply
for a loan (2 000–20 000, currency-agnostic), track it, and eventually sign
and pay; a back-office team reviews, scores, approves and services loans.
The full platform (§4 of the master prompt) spans several largely
independent subsystems — document upload, e-signature, payments/collections,
2FA, chatbot, KPI dashboards, scoring automation, SMS/email delivery. Building
all of it in one pass would produce a spec too large to implement or review
reliably.

This spec covers **Slice 1 only**: the foundation and one true end-to-end
flow — a client submits a loan application, it's visible and actionable in
the back-office, a staff member approves or rejects it, and the client's
dashboard reflects the outcome. Everything else is explicitly deferred (see
§8) to its own future spec.

## 2. Goals

- Prove the full path end-to-end: client submits → staff reviews/decides →
  client sees the outcome — before investing in any deferred subsystem.
- Establish the technical foundation (stack, schema, i18n, auth, design
  tokens) so later slices are additive, not restructuring.
- Get loan amount bounds (2 000–20 000) right as a single configurable
  constant, validated both client- and server-side, from the start.
- Real FR/EN parity on every screen built in this slice (not retrofitted).

## 3. Non-goals (this slice)

Explicitly out of scope for Slice 1 — see §8 for the full deferred list.
Nothing here should be designed against; deferred subsystems get their own
spec when their turn comes.

## 4. Stack

- Next.js (App Router) + TypeScript
- Tailwind CSS, design tokens per master prompt §3 (navy `#06171E`, neon
  green `#80FF4E`, serif headings / sans body) as CSS variables — no ad hoc
  colors/fonts
- PostgreSQL + Prisma ORM. Local dev was speced to run Postgres via Docker
  Compose (no external account required to start developing); during
  implementation Docker turned out not to be installed on the dev machine,
  while a native PostgreSQL 18 Windows service was already running. By
  agreement with the user, local dev uses that native service instead —
  a dedicated `espacecredit` role/database on it, created once by the user
  (who holds the postgres superuser credentials) rather than via
  `docker-compose.yml`. Same effect (a local Postgres, no third-party
  account), different provisioning mechanism.
- NextAuth.js, credentials provider, **two separate login flows**: `/login`
  (clients) and `/admin/login` (staff) — separate identity models so 2FA can
  be added to the staff flow later without touching client auth
- next-intl for FR (default) / EN, locale-prefixed routes (`/fr/...`,
  `/en/...`)
- pnpm
- Mutations via Next.js Server Actions (no separate REST/API layer for this
  slice — Server Actions are sufficient and idiomatic for App Router; an API
  layer can be introduced later if an external consumer needs one)
- Testing: Vitest + React Testing Library (unit/component), Playwright
  (end-to-end slice flow)

## 5. Data model

Prisma schema covers the full set of entities the master prompt's §7 asks
for, so later slices are additive migrations rather than restructuring.
Only the entities marked **[active]** are read/written by Slice 1 logic;
the rest are scaffolded empty and populated when their owning slice lands.

- **Client** [active] — id, email (unique), phone, passwordHash, firstName,
  lastName, locale, createdAt, updatedAt
- **StaffUser** [active] — id, email (unique), passwordHash, name,
  role (`AGENT | SUPERVISOR | ADMIN`), createdAt, updatedAt
- **LoanApplication** [active] — id, clientId, amount (constrained
  2 000–20 000 via DB check constraint + Zod), termMonths, rate,
  status (`DRAFT | SUBMITTED | IN_REVIEW | APPROVED | REJECTED`),
  formData (Json, per-step autosave payload), submittedAt, decidedAt,
  decidedByStaffId, decisionReason, createdAt, updatedAt
- **LoanScheduleEntry** [active] — id, applicationId, dueDate, amount,
  status (`UPCOMING | PAID | OVERDUE`) — generated by a simple amortization
  calculation at approval time so the client dashboard has real data to
  show; no payment collection/processing logic yet
- **Document** [scaffolded, unused] — id, applicationId, type, storageKey,
  uploadedAt (fields kept minimal; finalized when the upload slice lands)
- **Payment** [scaffolded, unused] — id, scheduleEntryId, amount, status,
  provider, providerRef, paidAt
- **NotificationLog** [scaffolded, unused] — id, recipientType, recipientId,
  channel, template, sentAt, status
- **AuditLog** [active] — id, actorType (`CLIENT | STAFF`), actorId, action,
  entityType, entityId, metadata (Json), createdAt — written on submit,
  approve, reject

Loan bounds live in one place, `lib/config/loan.ts`
(`MIN_LOAN_AMOUNT = 2000`, `MAX_LOAN_AMOUNT = 20000`), consumed by a shared
Zod schema used by both the client-side simulator/form and the server
action that persists the application. No component hardcodes these values.

## 6. Flows

### 6.1 Client application flow

Multi-step, progressive, autosaving form:

1. **Loan details** — simulator (amount slider + synced numeric input,
   bounds enforced live; term; live estimated-payment calculation), the
   hero interaction per master prompt §6
2. **Personal info**
3. **Employment / income info**
4. **Review & submit**

Each step change autosaves the in-progress `formData` to a `DRAFT`
`LoanApplication` row via a Server Action (upsert), so a refresh doesn't
lose progress. A persistent progress indicator shows step position.
Submitting the final step validates the full payload server-side and flips
status to `SUBMITTED`; writes an AuditLog entry.

### 6.2 Back-office flow

1. Staff logs in at `/admin/login`.
2. Case list at `/admin` — searchable/filterable table (status, client
   name, amount range, submission date), paginated. All three roles can
   view.
3. Detail view per application — client info, application data, decision
   controls. **Approve/reject is restricted to SUPERVISOR/ADMIN**; AGENT is
   view/search-only. This gives real role-scoped permissions from day one
   rather than deferring them.
4. Approving generates the `LoanScheduleEntry` rows (amortization over
   `termMonths` at `rate`) and writes an AuditLog entry with the decision
   and reason; rejecting writes AuditLog with the reason, no schedule.

### 6.3 Client dashboard

Shows the client's application(s) and current status. Once approved, shows
the generated payment schedule (read-only; no payment actions yet).

## 7. Security scope (this slice)

- Password hashing (bcrypt or argon2) for both Client and StaffUser
- Server-side validation (Zod) at every Server Action boundary — the trust
  boundary is the action input, not just the UI
- Route protection middleware: client routes require a Client session,
  `/admin/*` requires a StaffUser session; role check on the
  approve/reject action itself (not just hidden UI)
- HTTPS assumed at the hosting layer (out of scope per master prompt §5)

2FA, CAPTCHA/anti-bot, WAF-style hardening, and access logging beyond
AuditLog's submit/approve/reject coverage are deferred (§8) — Slice 1's
AuditLog only covers the actions this slice performs.

## 8. Deferred to future slices

Each of these gets its own brainstorming pass and spec when its turn comes;
nothing in this slice should be designed to anticipate their internals.

- Document upload & KYC storage (S3-compatible bucket, encryption at rest)
- Electronic signature integration
- Payments/collections provider integration (Paymely or equivalent),
  actual payment processing against `LoanScheduleEntry`
- 2FA for staff accounts
- CAPTCHA / anti-bot / WAF-style input hardening on public forms
- SMS/email delivery (transactional provider integration) — `NotificationLog`
  schema exists but nothing writes to it yet
- Scoring & automated approval-routing rules (this slice's approval is a
  manual staff decision)
- FAQ chatbot / virtual assistant
- CRM sync
- KPI dashboards & scheduled report generation
- Full audit trail beyond submit/approve/reject (e.g. "who viewed what")

## 9. Testing approach

- Vitest: loan-bounds validation, amortization calculation, role-permission
  checks on the approve/reject action
- React Testing Library: simulator (slider/input sync + bounds), multi-step
  form navigation + autosave
- Playwright: the full slice — client submits an application, staff logs in
  and approves it, client dashboard reflects APPROVED status and shows the
  schedule (and the reject variant)

None blocking — all decisions needed to start were resolved during

git-with-commits workflow, Vitest+RTL+Playwright).
